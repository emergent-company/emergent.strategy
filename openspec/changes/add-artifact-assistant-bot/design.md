# Design: Context-aware artifact authoring agent

## Context

This design assumes `add-artifact-patch-authoring` (the write primitive) and
`decide-authoring-agent-runtime` (the runtime and the tool-calling seam) have
landed. What follows is only what is specific to the agent.

Verified substrate, 2026-09-08:

| Concern | State |
|---|---|
| Chat UI | **None.** No templ file contains "chat"; DaisyUI's `chat` classes ship unused in `node_modules`. |
| Conversation storage | **None.** No conversations, messages or turns table. `adk_sessions` + 3 siblings exist (migration `034`), have no writer, and were explicitly retained by `039` for this agent. |
| SSE | `/strategies/:id/activity/stream` (`handler_activity_stream.go:28-96`) with client wiring in `shell.templ` including teardown, visibility handling, a 5-error circuit breaker and a 30s polling reconcile. |
| Activity events | 20 constants declared, 8 emitted, from 3 call sites. All 8 emissions use string literals rather than the constants. |
| Skill run ledger | `domain/skillrun`, migration `026`. Live. Reached automatically via the executor. |
| Agent card | `internal/agentcard/authoringbot.go` — published, `Status: planned`, hand-authored from the old proposal text. |
| Self-model | `internal/selfmodel`, 153 tools / 14 categories / 3 phases / 32 screens, generated by introspecting the real registration path, drift-checked. |

## Goals

- A conversational surface that produces reviewable staged changes, never commits.
- The second real agent, so `establish-agent-contract` is proven by use.
- No parallel mechanism where one already exists — ledger, activity stream, staging
  spine, session store.

## Non-Goals

- Token streaming (v1 streams progress events, not tokens).
- Multi-agent orchestration inside a turn beyond delegating to AIM.
- Replacing the skill path. Whole-artifact generation stays a skill.

## Decisions

### Decision 1 — The unit of work is a task, ended by staging or by the budget

A conversation is a sequence of units. A unit ends when the agent stages a change and
returns a review reference, when the turn bound is reached, or when the agent answers
without needing to write. The drawer staying open does not extend a unit.

**Why this matters more than it looks.** It is what makes compaction probably
unnecessary. If the unit is bounded and tool payloads are references (Decision 3),
the session does not accumulate the material that forces compaction in the first
place. `decide-authoring-agent-runtime` task 7.6 asks the question directly; this
design's answer is that a well-chosen unit removes the need. Compaction is the
mitigation for an unbounded session, and an unbounded session is a choice.

### Decision 2 — The human gate is out-of-band, so the agent does not suspend mid-turn

The agent stages a batch and ends its turn with a review reference. The human
approves on the review screen, which is a separate, already-durable surface.

This is deliberately different from `emergent.memory`, which built durable mid-turn
suspension (`SuspendSignal`, `PendingToolCallID` re-injection) because its gate is
inside the run. Ours is not.

**Consequence:** ADK's `toolconfirmation` protocol — the single strongest argument for
adopting ADK — is not a benefit for this agent. Notably `emergent.memory` also
declined to use it, for the mirror-image reason (theirs needed to survive a process
boundary; ADK's does not). `decide-authoring-agent-runtime` task 1.5 must confirm
this reading before the runtime decision leans on it either way.

If a clarifying question is needed mid-task, the agent asks it as an ordinary chat
turn and the user replies as an ordinary chat turn. That is a conversation, not a
suspended tool call.

### Decision 3 — Tool results are references, enforced by tool design

Every tool that can return a large payload returns `{ref, summary}`; the payload goes
to storage and is retrievable through the reference.

This is enforced at the tool boundary rather than by filtering the session, because
filtering the session means fighting the runtime — under ADK the runner appends every
non-partial event unconditionally. Designing the tool's return value is the only place
where the invariant holds regardless of runtime.

**The failure mode is observed, not theoretical.** `emergent.memory` writes each tool
result to `adk_events.content`, `agent_run_tool_calls.output`,
`agent_run_messages.content` and twice into `acp_run_events.data` — roughly 5×
amplification, every column unbounded — then compacts by summarising a transcript that
*skips function calls and results* (`session_compressor.go:121`). The payloads that
caused the growth contribute nothing to the compressed form. For an agent whose tools
return whole artifact payloads, that fails on day one.

### Decision 4 — Write gating is declarative data, and fails closed

Per-tool `{confirm, disabled}` policy as data, following `ToolPolicy`'s shape, applied
both when building tool definitions and at execution time.

**Fail closed.** If the gate cannot be evaluated, the tool does not run.
`emergent.memory` fails open (`executor.go:1620-1628`: log a warning, let it through).
That is a defensible choice for their knowledge agent; it is the wrong one for an
agent with a write set.

### Decision 5 — The card is generated from the running agent

`agentcard.AuthoringBot()` becomes generated from the agent's actual registered tool
set and gate configuration, the way `agentcard.AIM()` is generated from
`CycleWorkflow.CycleSteps()`. Its own doc comment currently concedes it is
*"deliberately not generated from running code the way AIM's card is"*.

`agent-contract` Requirement 1 requires generation and a drift check. A card that is
hand-copied from a proposal is the master-list-that-rots the contract exists to
prevent — and this one is already slightly ahead of reality, since it advertises three
skills that do not exist.

`internal/agentcard/card_test.go`'s `TestAIMAndAuthoringBot_DifferOnlyInChainPlanning
AndWriteSet` and `TestAuthoringBot_WriteSetIsNarrowerThanAIM` must keep passing once
the card is generated. They are the executable form of the baseline's one-agent-type
claim; if generation breaks them, either the agent grew a concept it should not have
or the baseline is wrong. Both outcomes are findings.

### Decision 6 — Delegation proof: authoring agent → AIM, in process

`establish-agent-contract/design.md` §4.a nominates this pair and calls it
*"deliberately trivial — proves staging/audit, not identity verification"*, on the
grounds that both live in the same process, same DB, same `context.Context`.

**That framing predates the DBOS cutover by one day and needs re-checking.** AIM is now
`internal/aimdbos.DBOSEngine` — a durable workflow that parks on `dbos.Recv`, can
resume in a different process, and outlives the inbound HTTP request whose context
carried the principal. "Same process, same `context.Context`" is a much weaker claim
against a durable workflow engine.

So the proof must answer a question §4.a did not ask: **does the initiating principal
survive a DBOS park/wake?** If it does not, delegated staging across an AIM gate
cannot attribute to the initiating human, and `agent-contract`'s "delegated change
reaches the initiating human" scenario fails for the very pair chosen to demonstrate
it. Better to find that here than in the contract document.

### Decision 7 — Reuse the activity stream; do not extend the dead constants

Progress rides the existing SSE fanout. The agent emits its own events.

Twelve of twenty activity constants are declared and never recorded, and all eight
live emissions use string literals rather than the constants — so the constant block
has no compile-time tie to reality. This change should not add to that. Either use the
constants and make them load-bearing for the events it emits, or do not add new ones.
Fixing the pre-existing twelve is out of scope and belongs with whoever next owns the
commit path.

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| Runtime decision lands differently than the working hypothesis | Everything above except Decision 5 is runtime-neutral. Decisions 1–3 constrain the runtime rather than depend on it. |
| Session growth despite Decisions 1 and 3 | Measure it. If a real conversation exceeds budget, revisit compaction with the two-phase shape but **not** the delete-then-recreate rebuild. |
| The card goes live before the agent is reachable | Flip `Status` in the same change that populates `URL`, and test that a `planned` card never carries a URL and a live one always does. |
| Delegation proof reveals the principal does not survive a DBOS gate | That is the proof doing its job. Record it as a contract finding; do not paper over it by choosing a pair that cannot fail. |
| Agent stages a batch the user did not intend | Every write is staged and reviewed; provenance from `add-artifact-patch-authoring` shows the agent as source; no commit tool exists. |

## Migration Plan

1. Agent skeleton + read-only tool set + mock agent. No writes.
2. Conversation persistence on the chosen store, org/user scoped.
3. Chat drawer + SSE progress. Read-only agent is already useful here.
4. Write tools behind the declarative gate, one tool (`propose_patch`) first.
5. Remaining write tools.
6. `delegation_chain` + the delegation proof + card generation + go live.

Steps 1–3 ship a genuinely useful read-only agent with no write risk at all.

## Open Questions

1. **Does the initiating principal survive a DBOS park/wake?** Decision 6. Must be
   answered by the proof, not assumed.
2. **Does the editability descriptor belong in the self-model?** Carried from
   `add-artifact-patch-authoring`. This change is the first consumer that would
   benefit — a remote agent needs to know which fields it may patch before trying.
3. **Does `ToolPolicy` become the estate-wide write-gating primitive?** Baseline open
   question 8. This is the second implementation; a third would be the point to
   reconcile rather than replicate.
